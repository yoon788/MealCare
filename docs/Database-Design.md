- 회원은 Firebase Authentication 계정과 일대일로 연결
- 현재 계정 유형은 환자 또는 보호자 중 하나
- 환자 한 명에게 여러 보호자를 연결할 수 있고, 보호자 한 명도 여러 환자를 관리할 수 있음
- 환자의 계획과 기록은 환자에게 소속, 보호자별로 같은 기록을 복제하지 않음
- 계획은 예정된 규칙이고, 기록은 실제 수행 결과
- 과거 기록에는 당시 계획의 버전과 필요한 정보를 보존
- 식별자에 사용하는 값은 생성 후 변경하지 않는다

공통 시각 속성

| 속성        | 자료형    | 적용 대상            | 의미                         |
|-------------|-----------|----------------------|------------------------------|
| `createdAt` | Timestamp | 모든 엔터티          | 서버가 기록한 최초 생성 시각 |
| `updatedAt` | Timestamp | 초대를 제외한 엔터티 | 업무 내용의 마지막 수정 시각 |

실제 복용·식사 시각은 사용자가 입력하는 사실 정보이므로, 서버가 기록하는 생성·수정 시각과 구분함.

날짜는 `YYYY-MM-DD`, 시각은 `HH:mm`, 요일은 월요일 1부터 일요일 7까지로 표현,  환자의 날짜와 일정을 해석할 때는 해당 계획·기록의 `timeZone`을 사용

---

1. 회원

환자와 보호자를 별도 회원 테이블로 나누지 않고, 하나의 회원 엔터티에서 계정 유형으로 구분

식별자: `uid`

```text
users/{uid}
publicProfiles/{uid}
```

| 속성               | 자료형    | 필수 여부 | 의미·제약                              |
|--------------------|-----------|-----------|----------------------------------------|
| `uid`              | 문자열    | 필수      | PK. Firebase Authentication UID        |
| `role`             | 열거형    | 필수      | `patient` 또는 `caregiver`             |
| `nickname`         | 문자열    | 필수      | 앱과 커뮤니티에 표시할 이름. 중복 허용 |
| `profileImagePath` | 문자열    | 선택      | 프로필 사진 저장 경로                  |
| `status`           | 열거형    | 필수      | `active`, `suspended`, `withdrawn`     |
| `createdAt`        | Timestamp | 필수      | 가입 시각                              |
| `updatedAt`        | Timestamp | 필수      | 회원 정보 수정 시각                    |

저장 범위는 다음과 같이 나눔

| 저장 위치              | 내용                                 |
|------------------------|--------------------------------------|
| `users/{uid}`          | 계정 유형, 회원 상태, 가입·수정 시각 |
| `publicProfiles/{uid}` | 닉네임, 프로필 사진                  |

두 문서는 하나의 회원 엔터티를 공개 범위에 따라 나누어 저장한 것

이메일·비밀번호·로그인 제공자는 Authentication에서 관리, 특히 비밀번호는 Firestore에 저장하지 않음

회원 상태는 서버에서 관리하며, 보호자 계정이라는 사실만으로 환자 기록에 접근할 수는 없음. 실제 접근 권한은 연결 엔터티로 판단

---

2. 환자–보호자 연결

연결 문서 하나는 환자 한 명과 보호자 한 명 사이의 관계를 나타냄

식별자: `(patientUid, caregiverUid)`  
저장용 식별자: 두 UID를 고정 조합한 `linkId`

```text
careLinks/{linkId}
```

| 속성           | 자료형    | 필수 여부 | 의미·제약                              |
|----------------|-----------|-----------|----------------------------------------|
| `linkId`       | 문자열    | 필수      | PK. 환자·보호자 UID 조합으로 고정 생성 |
| `patientUid`   | 문자열    | 필수      | FK. 환자 회원                          |
| `caregiverUid` | 문자열    | 필수      | FK. 보호자 회원                        |
| `status`       | 열거형    | 필수      | `active`, `revoked`                    |
| `permissions`  | Map       | 필수      | 연결별 공유 권한                       |
| `revokedAt`    | Timestamp | 해제 시   | 연결을 해제한 시각                     |
| `revokedByUid` | 문자열    | 해제 시   | FK. 해제를 요청한 회원                 |
| `createdAt`    | Timestamp | 필수      | 최초 연결 시각                         |
| `updatedAt`    | Timestamp | 필수      | 상태·권한 수정 시각                    |

`permissions`는 다음 세 가지로 구성

| 속성               | 자료형  | 의미                |
|--------------------|---------|---------------------|
| `readMeals`        | Boolean | 식사 기록 조회      |
| `readMedications`  | Boolean | 복약 계획·기록 조회 |
| `recordMedication` | Boolean | 복약 대리 기록      |

제약

- 두 회원은 서로 달라야 하며, 각각 환자·보호자 계정 유형에 맞아야 함
- 같은 환자–보호자 쌍의 연결은 하나만 존재
- 대리 기록을 허용하려면 복약 조회 권한도 있어야 함
- 공유 권한은 환자가 변경
- 연결 해제는 환자와 보호자 모두 가능
- 해제 후에도 환자의 기존 기록은 유지
- 재연결은 같은 문서를 재사용하고, 이전 변경 이력을 보존

`linkId`를 만들 때는 서로 다른 UID 조합이 같은 값이 되지 않도록 일관된 인코딩 규칙을 사용해야 함

---

3. 초대

환자가 공유 범위를 선택하여 발급하고, 보호자가 사용

식별자: 난수 초대 코드의 해시값인 `inviteId`

```text
invites/{inviteId}
```

| 속성          | 자료형    | 필수 여부 | 의미·제약                     |
|---------------|-----------|-----------|-------------------------------|
| `inviteId`    | 문자열    | 필수      | PK. 초대 코드 해시값          |
| `patientUid`  | 문자열    | 필수      | FK. 초대를 발급한 환자        |
| `permissions` | Map       | 필수      | 연결 성공 시 부여할 공유 권한 |
| `status`      | 열거형    | 필수      | `active`, `used`, `revoked`   |
| `createdAt`   | Timestamp | 필수      | 발급 시각                     |
| `expiresAt`   | Timestamp | 필수      | 만료 시각                     |
| `usedByUid`   | 문자열    | 사용 시   | FK. 초대를 사용한 보호자      |
| `usedAt`      | Timestamp | 사용 시   | 사용 성공 시각                |
| `revokedAt`   | Timestamp | 취소 시   | 사용 전 취소한 시각           |

적용 규칙은 다음과 같음

- 서버에서 영문 대문자·숫자 6자리 코드를 발급하며, 발급 후 10분 동안 유효함. 원문은 발급 시 전달하고 DB에는 해시만 저장함
- 초대 하나는 한 번만 사용
- 여러 보호자를 연결하려면 각각 초대를 발급
- 만료 여부는 서버 시각과 `expiresAt`으로 판단
- `status`가 `active`여도 만료 시각이 지났으면 사용할 수 없음
- 환자와 공유 권한은 발급 후 변경하지 않움
- 변경이 필요하면 취소 후 새로 발급함

초대 검증은 인증된 서버 함수에서 수행하며, 코드 검증 시도 횟수를 제한험

연결 생성·재활성화와 초대 사용 처리는 하나의 트랜잭션으로 완료. 두 보호자가 동시에 같은 초대를 사용해도 한 명만 성공해야 함

4. 약품

환자별 복용량과 일정을 약품 정보에 넣지 않음

식약처 API에서 선택한 약은 품목기준코드 `Drug.sourceItemId`로 식별합니다. 새 복약 계획에는 이 코드와 선택 당시의 `Drug.productName`을 각각 `sourceItemId`와 `drugName`으로 복사합니다. 식약처 품목을 선택할 때 공용 약품 문서를 생성할 필요는 없습니다.

아래 경로와 표는 이전 공용 약품 문서의 형식입니다. 여기의 `drugId`는 앱이 별도로 발급한 내부 ID입니다.

```text
drugs/{drugId}
```

| 속성               | 자료형    | 필수 여부         | 의미·제약                        |
|--------------------|-----------|-------------------|----------------------------------|
| `drugId`           | 문자열    | 필수              | PK. 내부 약품 ID                 |
| `productName`      | 문자열    | 필수              | 공식 제품명                      |
| `companyName`      | 문자열    | 선택              | 제조·수입업체명                  |
| `ingredients`      | 목록      | 선택              | 성분명, 제품 함량, 기준 단위     |
| `dosageForm`       | 문자열    | 선택              | 정제·캡슐·액제 등                |
| `prescriptionType` | 열거형    | 선택              | 전문·일반 구분. 모르면 미상 처리 |
| `imageUrl`         | 문자열    | 선택              | 제품 확인용 이미지               |
| `source`           | 문자열    | 외부 연동 시 필수 | 정보를 가져온 기관·데이터셋      |
| `sourceItemId`     | 문자열    | 외부 연동 시 필수 | 출처에서 사용하는 품목 식별 코드 |
| `officialInfoUrl`  | 문자열    | 선택              | 공식 상세 정보 주소              |
| `catalogStatus`    | 열거형    | 필수              | `active`, `archived`             |
| `createdAt`        | Timestamp | 필수              | 등록 시각                        |
| `updatedAt`        | Timestamp | 필수              | 정보 수정 시각                   |

외부 연동 시 `source + sourceItemId` 조합이 중복되지 않도록 관리, 외부 코드는 앞자리 0 등을 보존하기 위해 문자열로 저장.

`catalogStatus`는 앱 내부의 검색·선택 관리 상태이며 실제 허가·판매 상태를 뜻하지 않음. 보관 상태로 전환하더라도 과거 계획·기록의 참조는 유지

제품의 최신 상세 정보는 식약처 API에서 품목기준코드로 조회합니다.

5. 복약 계획

같은 환자가 같은 약품을 사용하더라도 기간이나 계획이 다를 수 있으므로 별도 식별자를 사용함

식별자: `planId`

```text
patients/{patientUid}/medicationPlans/{planId}
```

| 속성               | 자료형      | 필수 여부 | 의미·제약                     |
|--------------------|-------------|-----------|-------------------------------|
| `planId`           | 문자열      | 필수      | PK. 복약 계획 ID              |
| `patientUid`       | 문자열      | 필수      | FK. 계획의 소유자             |
| `sourceItemId`     | 문자열      | 신규 필수 | 식약처 품목기준코드. 앞자리 0도 보존 |
| `drugName`         | 문자열      | 신규 필수 | 계획 등록 당시의 공식 제품명  |
| `drugId`           | 문자열      | 이전 계획 | 기존 앱 내부 약품 ID          |
| `startDate`        | 날짜 문자열 | 필수      | 적용 시작일                   |
| `endDate`          | 날짜 문자열 | 선택      | 마지막 복용 예정일            |
| `timeZone`         | 문자열      | 필수      | 일정 해석 기준 시간대         |
| `doseSlots`        | 목록        | 필수      | 회차별 복용량·반복 일정       |
| `reminderSettings` | Map         | 필수      | 알림 활성화·반복 설정         |
| `status`           | 열거형      | 필수      | `active`, `paused`, `stopped` |
| `version`          | 정수        | 필수      | 계획 변경 버전                |
| `createdAt`        | Timestamp   | 필수      | 생성 시각                     |
| `updatedAt`        | Timestamp   | 필수      | 수정 시각                     |

각 `doseSlots` 항목은 다음 속성을 가짐

| 속성            | 필수 조건      | 의미                                |
|-----------------|----------------|-------------------------------------|
| `slotId`        | 항상           | 계획 안에서 회차를 구분하는 고정 ID |
| `doseAmount`    | 항상           | 1회 복용량                          |
| `doseUnit`      | 항상           | 복용량 단위                         |
| `daysOfWeek`    | 항상           | 반복 요일                           |
| `timingType`    | 항상           | `fixed` 또는 `mealRelative`         |
| `localTime`     | 고정 시각 방식 | 복용 예정 시각                      |
| `mealPlanId`    | 식사 연동 방식 | 같은 환자의 식사 계획 참조          |
| `offsetMinutes` | 식사 연동 방식 | 식전은 음수, 식후는 양수인 시간차   |

알림 설정에는 활성화 여부, 반복 간격, 최대 반복 횟수를 둠

제약은 다음과 같음

- 복용량은 양수이며 단위를 함께 저장
- 제품 함량과 환자의 복용량을 자동 환산하지 않음
- 종료일은 시작일 이상이어야 함
- 종료일이 지나면 새로운 복용 일정을 만들지 않음
- 환자와 선택한 약의 품목기준코드는 생성 후 고정합니다. Room에는 계획의 품목기준코드와 등록 당시 제품명을 함께 저장합니다. 이전 계획의 내부 ID와 이름은 보존하며, 품목기준코드를 확인할 수 없으면 `sourceItemId`는 비워 둡니다.
- 다른 약품으로 변경하려면 새 계획을 만듬
- 계획 변경은 환자만 가능하며, 보호자의 대리 기록 권한과 구분
- 일정·용량 변경 시 이전 버전과 적용 시점을 보존

6. 식사 계획

식별자: `mealPlanId`

```text
patients/{patientUid}/mealPlans/{mealPlanId}
```

| 속성               | 자료형      | 필수 여부 | 의미·제약                            |
|--------------------|-------------|-----------|--------------------------------------|
| `mealPlanId`       | 문자열      | 필수      | PK. 식사 계획 ID                     |
| `patientUid`       | 문자열      | 필수      | FK. 계획의 소유자                    |
| `mealType`         | 열거형      | 필수      | 아침·점심·저녁·간식·기타             |
| `mealName`         | 문자열      | 필수      | 화면에 표시할 식사 이름              |
| `weeklySchedule`   | 목록        | 필수      | 요일별 예정 시각                     |
| `timeZone`         | 문자열      | 필수      | 일정 해석 기준 시간대                |
| `startDate`        | 날짜 문자열 | 필수      | 적용 시작일                          |
| `endDate`          | 날짜 문자열 | 선택      | 마지막 식사 예정일                   |
| `reminderSettings` | Map         | 필수      | 알림 사용 여부·예정 시각 대비 시간차 |
| `status`           | 열거형      | 필수      | `active`, `paused`, `stopped`        |
| `version`          | 정수        | 필수      | 계획 변경 버전                       |
| `createdAt`        | Timestamp   | 필수      | 생성 시각                            |
| `updatedAt`        | Timestamp   | 필수      | 수정 시각                            |

`weeklySchedule` 항목에는 `daysOfWeek`와 `localTime`을 저장

예를 들어 한 아침 식사 계획에 평일 08시, 주말 09시를 함께 등록할 수 있음

- 한 계획 안에서 같은 요일이 중복되지 않도록 함
- 한 계획은 날짜당 한 번의 식사를 나타냄
- 간식이 여러 번이면 각각 별도 계획으로 등록함
- 계획 관리는 환자만 가능함
- 변경 시 이전 버전과 적용 시점을 보존함
- 복약 계획에서 참조 중인 식사 계획은 중단 상태로 보관함

7. 복약 기록

식별자: `planId + slotId + scheduleDate`를 고정 조합한 `recordId`

```text
patients/{patientUid}/medicationRecords/{recordId}
```

| 속성           | 자료형      | 필수 여부 | 의미·제약                            |
|----------------|-------------|-----------|--------------------------------------|
| `recordId`     | 문자열      | 필수      | PK. 회차별로 고정 생성               |
| `patientUid`   | 문자열      | 필수      | FK. 기록 대상 환자                   |
| `planId`       | 문자열      | 필수      | FK. 복약 계획                        |
| `slotId`       | 문자열      | 필수      | 계획 안의 복용 회차                  |
| `planVersion`  | 정수        | 필수      | 해당 회차에 적용된 계획 버전         |
| `scheduleDate` | 날짜 문자열 | 필수      | 회차가 배정된 환자 기준 날짜         |
| `timeZone`     | 문자열      | 필수      | 해당 회차의 시간대                   |
| `scheduledAt`  | Timestamp   | 필수      | 해당 회차의 복용 예정 시각           |
| `doseSnapshot` | Map         | 필수      | 당시 약품 ID·제품명·복용량·단위      |
| `status`       | 열거형      | 필수      | `taken`, `notTaken`, `voided`        |
| `takenAt`      | Timestamp   | 선택      | 실제 복용 시각. 정확히 모르면 미입력 |
| `createdByUid` | 문자열      | 필수      | FK. 최초 작성자                      |
| `updatedByUid` | 문자열      | 필수      | FK. 마지막 수정자                    |
| `revision`     | 정수        | 필수      | 기록 수정 버전                       |
| `note`         | 문자열      | 선택      | 미복용 사유 등 메모                  |
| `createdAt`    | Timestamp   | 필수      | 서버 저장 시각                       |
| `updatedAt`    | Timestamp   | 필수      | 마지막 수정 시각                     |

상태는 다음 의미로 사용함

| 상태       | 의미                              |
|------------|-----------------------------------|
| `taken`    | 복용했음을 확인                   |
| `notTaken` | 복용하지 않았음을 명시적으로 확인 |
| `voided`   | 잘못 입력하여 취소                |

작성·수정 규칙은 다음과 같음

- 환자 또는 대리 기록 권한이 있는 보호자가 작성함
- 환자는 본인 기록 전체를 수정할 수 있음
- 보호자는 현재 권한이 유효할 때 본인이 작성한 기록만 수정할 수 있음
- 작성자와 계획·약품 정보는 서버에서 검증함
- 수정·취소 이력을 보존함
- `revision` 비교와 트랜잭션으로 동시 수정 충돌을 처리함

`planVersion`은 식별자에 포함하지 않음 계획 버전이 달라져도 같은 날짜·회차의 기록은 하나로 유지함

실제 복용이 다음 날 이루어져도 `scheduleDate`는 유지하고 실제 시각은 `takenAt`으로 구분함

8. 식사 기록

식별자: `mealPlanId + scheduleDate`를 고정 조합한 `recordId`

```text
patients/{patientUid}/mealRecords/{recordId}
```

| 속성           | 자료형      | 필수 여부 | 의미·제약                        |
|----------------|-------------|-----------|----------------------------------|

| `timeZone`     | 문자열      | 필수      | 해당 식사의 시간대               |
| `scheduledAt`  | Timestamp   | 필수      | 식사 예정 시각                   |
| `mealSnapshot` | Map         | 필수      | 당시 식사 구분·이름              |
| `status`       | 열거형      | 필수      | `completed`, `skipped`, `voided` |

| `revision`     | 정수        | 필수      | 기록 수정 버전                   |
| `note`         | 문자열      | 선택      | 결식 사유 등 메모                |
| `createdAt`    | Timestamp   | 필수      | 서버 저장 시각                   |
| `updatedAt`    | Timestamp   | 필수      | 마지막 수정 시각                 |

| 상태        | 의미                       |
|-------------|----------------------------|
| `completed` | 식사 완료를 확인           |
| `skipped`   | 결식했음을 명시적으로 확인 |

현재 권한 설계에서는 환자만 작성·수정함 보호자는 활성 연결의 `readMeals` 권한이 있을 때 조회함

`completedAt`은 정확히 모르면 미입력할 수 있으며, 결식·취소 상태에서는 비워 둠. 수정 이력과 동시 수정 처리는 복약 기록과 같은 방식으로 관리함

복약·식사 기록 모두 기록이 없거나 취소된 경우는 ‘미확인’. 예정 시각이 지났다는 이유만으로 미복용·결식 처리하지 않음

9. 게시글

식별자: `postId`

```text
posts/{postId}
```

| 속성           | 자료형    | 필수 여부 | 의미·제약                       |
|----------------|-----------|-----------|---------------------------------|
| `postId`       | 문자열    | 필수      | PK. 별도 발급                   |
| `authorUid`    | 문자열    | 필수      | FK. 작성한 회원                 |
| `category`     | 열거형    | 필수      | 게시글 분류                     |
| `title`        | 문자열    | 필수      | 제목                            |
| `body`         | 문자열    | 필수      | 일반 텍스트 본문                |
| `status`       | 열거형    | 필수      | `published`, `deleted`          |
| `commentCount` | 정수      | 필수      | 삭제되지 않은 댓글 수. 초기값 0 |
| `createdAt`    | Timestamp | 필수      | 최초 등록 시각                  |
| `updatedAt`    | Timestamp | 필수      | 제목·본문·카테고리 수정 시각    |
| `deletedAt`    | Timestamp | 삭제 시   | 삭제 시각                       |

카테고리는 다음 다섯 종류.

- 건강 정보
- 식사 이야기
- 복약 경험
- 생활 팁
- 자유 이야기

DB에는 표시명과 구분한 코드값을 저장함

관리 규칙은 다음과 같음

- 제목과 본문은 공백만으로 작성할 수 없음
- 공개된 게시글은 로그인 회원이 조회함
- 작성자만 수정·삭제할 수 있음
- 작성자와 최초 작성 시각은 변경하지 않음
- 작성자 닉네임·사진은 공개 프로필에서 조회함
- 댓글 수는 서버에서 관리함
- 댓글 수 갱신은 게시글 내용의 수정 시각을 바꾸지 않음
- 삭제된 게시글과 그 댓글은 일반 조회 대상에서 제외함

10. 댓글

식별자: `commentId`

```text
posts/{postId}/comments/{commentId}
```

| 속성        | 자료형    | 필수 여부 | 의미·제약              |
|-------------|-----------|-----------|------------------------|
| `commentId` | 문자열    | 필수      | PK. 별도 발급          |
| `postId`    | 문자열    | 필수      | FK. 댓글이 속한 게시글 |
| `authorUid` | 문자열    | 필수      | FK. 작성한 회원        |
| `body`      | 문자열    | 필수      | 일반 텍스트 본문       |
| `status`    | 열거형    | 필수      | `published`, `deleted` |
| `createdAt` | Timestamp | 필수      | 최초 등록 시각         |
| `updatedAt` | Timestamp | 필수      | 본문 수정 시각         |
| `deletedAt` | Timestamp | 삭제 시   | 삭제 시각              |

관리 규칙은 다음과 같음

- 본문은 공백만으로 작성할 수 없음
- 게시글과 댓글이 모두 공개 상태일 때 로그인 회원이 조회함
- 삭제된 게시글에는 새 댓글을 작성할 수 없음
- 수정·삭제는 댓글 작성자만 가능함
- 게시글·작성자 참조와 최초 작성 시각은 변경하지 않음

게시글의 `commentCount`는 다음과 같이 처리함

| 작업           | 댓글 수 변경 |
|----------------|-------------:|
| 댓글 생성      |           +1 |
| 댓글 최초 삭제 |           −1 |
| 본문 수정      |    변경 없음 |

댓글 생성·삭제와 댓글 수 변경은 하나의 서버 트랜잭션으로 처리하며, 같은 요청이 재시도되어도 한 번만 반영함

엔터티 사이의 관계는 다음과 같음 아래에서 `1:N`의 N 쪽은 모두 0개 이상을 허용함

| 부모·참조 대상 | 자식·참조하는 엔터티 | 관계와 의미                                     |
|----------------|----------------------|-------------------------------------------------|
| 회원           | 환자–보호자 연결     | 환자 역할로 `1:N`                               |
| 회원           | 환자–보호자 연결     | 보호자 역할로 `1:N`                             |
| 회원           | 연결 해제자          | 연결 하나에 해제자는 `0~1명`                    |
| 회원           | 초대                 | 발급 환자 기준 `1:N`                            |
| 회원           | 초대 사용            | 초대 하나에 사용 보호자는 `0~1명`               |
| 회원           | 복약 계획            | 환자 기준 `1:N`                                 |
| 회원           | 식사 계획            | 환자 기준 `1:N`                                 |
| 식약처 약품    | 복약 계획            | 품목기준코드 기준 `1:N`                       |
| 복약 계획      | 복약 기록            | `1:N`                                           |
| 식사 계획      | 식사 기록            | `1:N`                                           |
| 회원           | 복약·식사 기록       | 대상 환자·최초 작성자·마지막 수정자로 각각 참조 |
| 식사 계획      | 복약 계획            | 회차별 식사 참조를 통한 선택적 `N:M`            |
| 회원           | 게시글               | 작성자 기준 `1:N`                               |
| 게시글         | 댓글                 | `1:N`                                           |
| 회원           | 댓글                 | 작성자 기준 `1:N`                               |

환자와 보호자의 다대다 관계는 연결 엔터티가 중간에서 해소함

식사 계획과 복약 계획의 관계는 `doseSlots[].mealPlanId`로 표현함 복용 회차 하나는 식사 계획을 최대 하나 참조하지만, 여러 회차가 서로 다른 식사를 참조할 수 있으므로 계획 전체로 보면 선택적 다대다.

초대 사용은 연결을 생성·재활성화하는 업무 흐름. 현재 초대와 연결 사이의 직접 FK 필드는 정의하지 않음
